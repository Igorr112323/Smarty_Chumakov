# Промты для ИИ: сборка и приёмка модуля SpanVerify

Пакет из четырёх промтов для генерации рабочего приложения силами ИИ
(Claude, ChatGPT, Gemini, DeepSeek, локальные модели) и один короткий — для
Cursor/Copilot. Промты согласованы с уже реализованным модулем
`spanverify-module/`, поэтому результат можно сравнить с рабочим эталоном.

**Как пользоваться:** копируйте промт целиком, одним сообщением. Если модель
обрывает ответ — пишите «продолжи с файла X» и прикладывайте предыдущий вывод.

**Важно про цифры.** Все промты требуют честной отчётности: качество
подтверждается только на размеченных данных в режиме реальной модели. Если
модель начинает выдавать «точность 98 %» без прогона на данных — это признак
выдуманного результата.

## Промт 1. Собери приложение целиком

> Ты — инженер-разработчик. Собери законченный Python-проект `spanverify` —
> локальный анализатор, который находит в тексте фрагменты, написанные
> языковой моделью, и оценивает долю участия ИИ.
>
> **Жёсткие требования**
> 1. Только стандартная библиотека Python 3.10+ для ядра, CLI, HTTP API и
>    веб-интерфейса. Ничего нельзя импортировать из сторонних пакетов в
>    базовом режиме (numpy, torch, fastapi — запрещены).
> 2. Проект должен запускаться сразу после распаковки: `python -m spanverify selftest`
>    и `python -m spanverify serve` обязаны работать без установки зависимостей.
> 3. Никаких сетевых обращений и передачи текста наружу. Всё локально.
> 4. Код — на русском в docstring-ах и сообщениях, идентификаторы — на английском.
>
> **Функциональность**
> * `Detector.analyze(text, threshold=None)` возвращает: `verdict`
>   (`likely_ai` | `mixed` | `likely_human`), `ai_fraction` (доля символов,
>   покрытых найденными фрагментами), `ai_fraction_soft` (ожидаемая доля),
>   `ai_fraction_tokens`, `spans[]`, `warnings[]`, `meta`.
> * Каждый фрагмент (`Span`): `index`, `start_char`, `end_char`, `start_token`,
>   `end_token`, `n_tokens`, `mean_prob`, `peak_prob`, `text`.
> * Конвейер: токенизация с непрерывным покрытием текста → признаки по
>   токенам → взвешенная сырая оценка → сглаживание скользящим средним →
>   изотоническая калибровка (PAVA) → порог → фрагменты → расширение до
>   границ предложений и склейка соседних → ограничение на минимальную длину.
> * Два бэкенда: `surrogate` (демо, без зависимостей: повторяемость
>   содержательных слов, шаблонные обороты и их плотность в окне, локальная
>   повторяемость, единообразие ритма; служебные слова помечаются
>   неинформативными и восстанавливаются по окружению) и `hf` (энтропия
>   внимания последнего слоя `1 − H/log(n)` + kNN-плотность контекстных
>   эмбеддингов, `k = 5`; `torch`/`transformers` подключаются лениво и их
>   отсутствие не должно ломать импорт).
> * Калибровка: `IsotonicCalibrator` (метод смежных нарушителей, сжатие
>   ступенчатой функции при сохранении монотонности), подбор порога как
>   максимум F1 при ограничении `FPR ≤ max_fpr` (по умолчанию 0.1),
>   5-фолдовая кросс-валидация.
> * CLI: `analyze` (--text/--file/stdin, --json, --explain), `demo`,
>   `calibrate`, `serve`, `selftest`, `config`.
> * HTTP API на `http.server.ThreadingHTTPServer`: `GET /health`,
>   `GET /v1/config`, `GET /v1/model`, `POST /v1/verify` (тело
>   `{"text": ..., "threshold": ..., "explain": bool}`, лимит 4 МБ, аккуратные
>   коды 400/404/500), CORS-заголовки.
> * Веб-интерфейс — один HTML-файл, встроенный в Python-модуль, без CDN и
>   сборки: поле ввода, кнопка «Проверить», шкала доли ИИ, разметка текста
>   `<mark>`, таблица фрагментов, необязательная покадровая таблица.
>   Запросы только по относительным адресам, чтобы работать за прокси.
> * Синтетический генератор корпуса `demo_data` с разметкой по символам
>   `[[start, end, label], ...]`, JSONL-запись/чтение и статистика корпуса.
> * Тесты на `pytest`, не менее 60 штук: токенизация, векторы, калибровка
>   (включая ручную проверку метрик), конфиг, ядро, API, генератор, бэкенды.
>
> **Обязательная честность**
> * В демо-режиме каждый ответ содержит предупреждение, что проверяется
>   конвейер, а не достоверность текста.
> * Никаких заявлений о качестве без прогона на размеченных данных; в
>   README должно быть прямо написано, что метрики на синтетике не
>   переносятся на реальные документы.
>
> **Что выдать**
> Дерево файлов и полное содержимое каждого файла (не сокращать, не писать
> «остальное аналогично»). Затем — команды для запуска и проверки:
> `python -m spanverify selftest`, `python -m pytest -q`.
>
> **Критерии приёмки**
> 1. `python -m spanverify selftest` — все проверки OK.
> 2. `python -m spanverify analyze --text "Важно отметить, что данный метод обеспечивает эффективное решение поставленной задачи" --json` — вердикт `likely_ai`.
> 3. Человеческий текст с конкретикой (фамилии, числа, даты) — `likely_human`.
> 4. `python -m pytest -q` — все тесты проходят.

## Промт 2. Собери исполняемый файл (Windows `.exe` без Windows-машины)

> Собери поставку SpanVerify в один исполняемый файл.
>
> **Что нужно сделать**
> 1. `spanverify.spec` для PyInstaller: точка входа `app.py` (при запуске без
>    аргументов поднимает сервис и открывает браузер), `console=True`,
>    данные `config/` и `data/` кладутся рядом с бинарником
>    (`datas`), исключения для `torch/transformers/streamlit/pandas`, чтобы
>    демо-сборка осталась компактной.
> 2. `scripts/make_exe.ps1` (PowerShell, Windows): проверка версии Python
>    ≥ 3.10, установка зависимостей, прогон тестов, обучение калибратора,
>    если `config/calibration.json` отсутствует, сборка, комплектация
>    папки `release/` (exe + config + data + README) и обязательная проверка
>    `release\spanverify.exe selftest`.
> 3. `scripts/build.sh` (Linux/macOS) — то же для бинарника без расширения,
>    плюс `scripts/build_zipapp.sh`, который собирает один
>    переносимый файл `release/spanverify.pyz` (ему нужен Python на целевой
>    машине, зато сборка работает где угодно). Внутри zipapp конфиг и
>    калибратор должны читаться из архива (`zipfile` + `sys.argv[0]`).
> 4. `.github/workflows/build-windows-exe.yml`: workflow
>    `build-windows-exe` на `windows-latest`, запуск вручную и по тегу `v*`;
>    шаги: установка Python 3.11 → зависимости → тесты → калибровка →
>    PyInstaller → проверка `selftest` → выгрузка артефакта
>    `spanverify-windows-x64`; при теге — публикация в Releases.
> 5. README: раздел про сборку с честным указанием ограничений.
>
> **Обязательные оговорки**
> * PyInstaller не кросс-компилирует: `.exe` собирается только на Windows или
>   в CI на Windows-раннере.
> * Для сборки на Linux нужна разделяемая библиотека Python
>   (`libpython3.x.so`); в минимальных образах она отсутствует — это
>   ограничение окружения, и его нужно явно описать, а не обходить
>   выдуманными результатами.
> * Не утверждай, что `.exe` проверен, если он не запускался. Напиши, что
>   именно проверено (сборка, `selftest`, запуск сервиса), а что нет.
>
> **Что выдать:** все файлы целиком, команды сборки для Windows и для CI,
> ожидаемый размер результата и список проверок после сборки.

## Промт 3. Реальный режим модели и эксперименты на своём корпусе

> Доведи SpanVerify до боевого режима и сними отчёт по качеству.
>
> **1. Бэкенд `hf`**
> * Модель по умолчанию `cointegrated/rubert-tiny2` (конфигурируемая), загрузка
>   ленивая, `output_attentions=True`, `output_hidden_states=True`.
> * Признак предсказуемости: энтропия внимания последнего слоя, усреднённая
>   по головам, нормированная на `log(seq_len)`, затем `1 − H_norm`.
> * Контекстные векторы: скрытое состояние последнего слоя, усреднённое по
>   сабтокенам слова (по `offset_mapping`), спроецированное в хешированное
>   пространство фиксированной размерности.
> * Если `torch`/`transformers` не установлены — понятная ошибка
>   `BackendUnavailable` с командой установки, без падения импорта.
> * Поддержка длинных документов: нарезка на окна с перекрытием и склейка
>   оценок без разрывов на границах.
>
> **2. Датасет.** Формат JSONL: `{"id": "...", "text": "...", "labels":
> [[start, end, 1], ...]}`. Нужно 100+ документов и 20–30 тыс. токенов,
> разметка по абзацам/фрагментам (не по словам). Опиши, как собрать корпус
> (документы: написанные человеком, сгенерированные, отредактированные
> человеком после генерации; важно указать, кто и как размечал).
>
> **3. Эксперименты** `scripts/run_experiments.py`:
> * разбиение по документам 70/30, обучение калибровки только на обучающей
>   части, оценка на отложенной (никакой утечки между частями);
> * метрики по токенам (precision, recall, F1, FPR, HDR), по фрагментам
>   с IoU ≥ 0.5 и ≥ 0.25, по символам (precision/recall/F1, средний IoU),
>   ошибка оценки доли участия ИИ (MAE и максимум);
> * baseline «всё — ИИ» и абляции: только предсказуемость, только плотность,
>   полный набор;
> * сетка порогов с таблицей F1/FPR;
> * отчёт `report.md`, машиночитаемый `report.json` и SVG-график
>   распределения вероятностей по классам (без matplotlib).
> * Запуск: `python scripts/run_experiments.py --dataset data/real.jsonl --backend hf --out reports/real`.
>
> **4. Честность выводов.** В отчёте отдельно: объём корпуса, кто размечал,
> как считался FPR, какие ошибки типичны (пропуски коротких вставок, ложные
> срабатывания на канцелярите). Любые утверждения о превосходстве над
> baseline — только с числами и с указанием доверительных интервалов
> (bootstrap допустим).
>
> **Что выдать:** код, команды, таблицы метрик и текстом — что можно и чего
> нельзя утверждать по этим результатам.

## Промт 4. Приёмка результата

> Проверь приложение SpanVerify на соответствие спецификации и выдай
> протокол приёмки.
>
> 1. Запусти `python -m spanverify selftest` и `python -m pytest -q`, приведи
>    вывод целиком.
> 2. Прогони три текста: (а) чистый машинный, (б) человеческий с
>    конкретикой, (в) смешанный документ. Для каждого покажи вердикт, долю
>    ИИ, найденные фрагменты и предупреждения.
> 3. Проверь API: `GET /health`, `POST /v1/verify` (валидный и невалидный
>    запрос), `GET /v1/config`. Покажи фактические ответы и коды.
> 4. Проверь, что в демо-режиме предупреждение присутствует в каждом ответе
>    и что в README нет утверждений о качестве без данных.
> 5. Составь таблицу «требование — выполнено/нет — доказательство
>    (команда и вывод)». Отдельно перечисли: что не проверено, какие
>    ограничения среды (нет GPU, нет Windows), какие риски.
> 6. Ничего не додумывай: если проверить нельзя — так и напиши.
>
> Формат ответа: протокол с командами, выводами и итоговым вердиктом
> «принято / принято с замечаниями / не принято» и списком замечаний.

## Короткий промт для Cursor / Copilot (вставка в чат редактора)

> Реализуй по спецификации модуль определения ИИ-текста в этом проекте:
> конвейер «токенизация → признаки → сырая оценка → сглаживание →
> изотоническая калибровка (PAVA) → порог при FPR ≤ 0.1 → фрагменты →
> расширение до границ предложений», stdlib-only, CLI (`analyze`, `demo`,
> `calibrate`, `serve`, `selftest`, `config`), HTTP API на `http.server`
> (`/health`, `/v1/verify`), однофайловый веб-интерфейс, тесты pytest.
> Демо-режим обязан выдавать предупреждение, что он не оценивает
> достоверность текста. Соблюдай стиль существующего кода, docstring-и на
> русском, никаких новых зависимостей в базовом режиме.

## Что проверить за 5 минут после генерации кода

| Проверка | Команда | Ожидаемый результат |
|---|---|---|
| Ядро живо | `python -m spanverify selftest` | все проверки `[OK]` |
| Демо не врёт | `python -m spanverify analyze --text "..."` | есть предупреждение о демо-режиме |
| Машинный текст | промт 1, критерий 2 | `likely_ai`, фрагменты найдены |
| Человеческий текст | текст с именами и цифрами | `likely_human`, 0 фрагментов |
| API | `curl localhost:8000/health` | `{"status":"ok", ...}` |
| Тесты | `python -m pytest -q` | 0 падений |
| Нет лишних зависимостей | `grep -rE "^(import|from) (numpy|torch|fastapi|streamlit)" spanverify/` | пусто в базовом режиме |
| Нет выдуманных метрик | поиск «98 %», «точность 0.99» в README | таких чисел без данных быть не должно |

## Как понимать результаты

* `surrogate` — проверка конвейера. Числа этого режима нельзя переносить в
  отчётность: они измеряют согласованность с синтетическим генератором.
* `hf` — целевой режим. Метрики имеют смысл только вместе с описанием
  корпуса, разметки и порога.
* Порог подбирается под ограничение `FPR ≤ 0.1`: это осознанный выбор в
  пользу осторожности — лучше пропустить машинный фрагмент, чем обвинить
  человеческий текст.
