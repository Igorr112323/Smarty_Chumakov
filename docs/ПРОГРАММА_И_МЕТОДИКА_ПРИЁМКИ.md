# Программа и методика приёмки SpanVerify

Документ закрывает требование раздела 7 ТЗ на программу (`docs/ГОСТ/ТЗ_на_программу.md`):
приёмка идёт по этой программе и методике. Все числа ниже берутся из единого
файла чисел `spanverify-module/reports/METRICS.json`; если файл и документ
расходятся, правится документ, а не файл.

## 1. Объект приёмки

* Программа SpanVerify, версия релиза одна — из `meta.version` файла
  `reports/METRICS.json` (сейчас 1.3.0); версия пакета
  (`spanverify/_version.py`) и метаданных сборки (`pyproject.toml`) обязаны
  совпадать (проверка `tests/test_version.py`).
* Формы поставки: пакет `spanverify`, CLI `python -m spanverify`, HTTP-сервер,
  сборка `.exe`/`.pyz` (при наличии артефактов — их контрольные суммы в
  `release/SHA256SUMS.txt`).

## 2. Условия проведения

* Python 3.10–3.12, ОС Linux или Windows; CPU, без GPU.
* Зависимости: `spanverify-module/requirements.txt` (ядро работает на
  стандартной библиотеке; зависимости нужны для тестов и сборки).
* Режим `hf` (признаки реальной языковой модели) выполняется только на раннере
  GitHub и в приёмку демо-критериев не входит: его числа попадают в
  `reports/METRICS.json` отдельными блоками (`hf_experiments`,
  `hf_external_slices`) и приёмочными не считаются, пока не измерены заново
  текущей версией кода.

## 3. Порядок проверки (программа испытаний)

| № | Проверка | Команда | Критерий |
| --- | --- | --- | --- |
| 1 | Линтер | `cd spanverify-module && ruff check .` | 0 замечаний |
| 2 | Форматирование | `black --check .` | файлы не требуют правки |
| 3 | Тесты | `python -m pytest -q` | все проходят |
| 4 | Покрытие | `python -m pytest --cov=spanverify --cov-fail-under=85` | не ниже 85 % |
| 5 | Демо-критерий качества | `python -m spanverify evaluate --dataset data/demo_pairs.jsonl` | значения из `reports/METRICS.json` |
| 6 | Воспроизводимость | два запуска `python -m spanverify train --dataset data/demo_pairs.jsonl --seed 42` | одинаковые контрольные суммы `weights.json`, `head.json`, `participation.json` |
| 7 | Сверка чисел в документах | `python scripts/check_numbers.py` | 0 расхождений с `reports/METRICS.json` |
| 8 | Работоспособность сервера | `python -m spanverify server` + запрос `/health` и `/v1/verify` | `status=ok`, вердикт по подмене числа |
| 9 | Функциональные испытания | `reports/FUNCTIONAL_TESTS.md`, `python scripts/functional_tests.py` | коды возврата 0/1/2, предельная длина обработана |

Одна сводная команда пунктов 1–3 и 7:

```
cd spanverify-module && ruff check . && black --check . && python -m pytest -q && python scripts/check_numbers.py
```

## 4. Методика: как читаются результаты

1. **Демо-критерий (пункт 5).** Критерий из ТЗ (раздел 1.6) проверяется на
   демонстрационном корпусе: `token F1` и `FPR` из блока `demo.in_corpus`
   файла `reports/METRICS.json` (измерено: 0.953 при FPR 0.002). Демо-корпус
   синтетический — это фиксируется оговоркой в `reports/METRICS.json`
   (`disclaimer`) и не считается научным результатом.
2. **Отсутствие подбора порога по тесту.** Порог решения и маска выбираются
   только на обучающей части (`spanverify/train.py`); официальный тест корпусов
   в выборе не участвует. Экспериментальный отчёт
   (`scripts/run_experiments.py`) обязан показывать официальный тест отдельным
   блоком и содержать кривую маски на обучающей части.
3. **Числа режима `hf`.** Берутся только из файлов прогонов
   (`reports/experiments/*/experiment.json`, `reports/ext_*_hf.json`) и только
   после того, как их собрал `scripts/collect_metrics.py` в
   `reports/METRICS.json`. Журналы (`PROGRESS.md`, `AUDIT.md`) цитируют файл
   эксперимента только вместе с номером прогона.
4. **Вердикты.** Правило вердикта уровня ответа — «одиночный токен маски не
   обвиняет ответ» (`min_two_tokens`); фрагменты текстовых правил (привязка
   числа к объекту) решают и в одиночку. Сравнение старого и нового правила на
   одном тесте приводится в файле эксперимента
   (`verdict_rule_comparison`).

## 5. Правило приёмки

Программа считается прошедшей приёмку, если пункты 1–8 таблицы выполнены, а
расхождения по пункту 7 отсутствуют. Падение любого пункта — отказ; результат
фиксируется протоколом со ссылкой на прогон (номер прогона или локальная
команда и дата).

## 6. Что приёмка не утверждает

* Качество на реальных документах: демо-корпус синтетический; числа корпуса A3
  (реальные акты) и внешних наборов приводятся в `reports/METRICS.json` как
  измерение, а не как приёмочный критерий.
* Любые непрогнозируемые приросты: в протокол попадают только числа из файлов
  прогонов и команды, которыми они получены.
