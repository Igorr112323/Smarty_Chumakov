# Методика разметки корпуса пар «документ — ответ»

Версия методики: **1.3.0** — совпадает с версией пакета `spanverify` (`meta.version` в
`spanverify-module/reports/METRICS.json`) и с версией объекта приёмки
(`docs/ПРОГРАММА_И_МЕТОДИКА_ПРИЁМКИ.md`). Дата фиксации редакции: 2026-10-11.

Основание: договор № 0117812 (УМНИК), этап 1, работы 1–2 («методика разметки и описание
признаков», «документ с указанием версии»). Описание признаков и их информативность —
отдельный документ, `docs/ПРИЗНАКИ.md`.

## 1. Что размечается и в каком объёме

Единица разметки — **пара**: `context` (фрагмент документа) и `answer` (текст ответа модели
на вопрос по этому документу). Размечается **только ответ**: отмечаются фрагменты ответа,
которые не подкрепляются документом. Документ — неизменяемый источник, его разметка не
требуется.

Три уровня меток, все три выводятся из одного и того же списка `labels`:

| Уровень | Что это | Как получается |
|---|---|---|
| токен | токен ответа помечен как недостоверный, если он пересекается хотя бы с одним размеченным фрагментом | пересечение границ токена с `labels` |
| фрагмент (span) | отрезок ответа `answer[start:end]`, ровно тот, что указан разметчиком | напрямую из `labels` |
| ответ | в ответе есть хотя бы один недостоверный фрагмент | непустой `labels` |

Канон определений и формул метрик — `spanverify-module/docs/METRIC_SPEC.md` (v1) и
`spanverify-module/docs/METRIC_SPEC_v2.md` (v2). Оба файла защищены тестами на неизменность
хеша: после публикации чисел определения не меняются.

## 2. Формат записи

Одна пара — одна строка JSON Lines:

```json
{"id": "pair-00001", "context": "текст документа", "answer": "текст ответа",
 "labels": [[20, 23, 1]], "meta": {"kind": "number_attribution", "source": "…"}}
```

Правила, обязательные для разметчика (совпадают с текстом шаблона
`spanverify-module/scripts/make_markup_template.py`):

* `labels` — **только** недостоверные фрагменты; правильные места не размечаются; пустой
  список означает «в ответе всё верно»;
* границы указываются **по символам ответа**, нумерация с нуля, правая граница-exclusive:
  выполняется `answer[start:end] == span`;
* интервал записывается тройкой `[начало, конец, 1]`, третий элемент — флаг «недостоверно»
  (разметка «подтверждено» не требуется: отсутствие метки и есть подтверждение);
* перекрывающиеся интервалы не допускаются — их сливают до записи;
* пунктуация, союзы и отдельные служебные слова не размечаются: конвейер их не оценивает,
  и разметка «на всякий случай» смещает метрику уровня токена;
* фрагмент не должен начинаться или заканчиваться пробелом.

Заготовка для собственных документов:

```bash
cd spanverify-module
python3 scripts/make_markup_template.py --out data/мои_пары.jsonl --count 30
```

## 3. Автоматическая разметка по построению (способ 1)

Для корпусов A1 и A3 метка не назначается «на глаз»: она **возникает из генерации**.
Генератор знает, какое значение он подставил в ответ и откуда, поэтому границы
недостоверного фрагмента известны до разметки.

* A1 (`scripts/build_corpus_a.py`): документы тоже генерируются, каждая пара несёт
  `meta.synthetic_document = true`.
* A3: документы **настоящие** — тексты официально опубликованных актов, загруженные
  `scripts/fetch_npa_corpus.py` и лежащие в `spanverify-module/data/corpus_a3/sources/`
  (409 файлов, хеш каждого — в манифесте). Пары собирает `scripts/build_corpus_a.py --real`,
  который вызывает `scripts/corpus_real.py`: извлечение фактов из реального текста
  (`extract_facts`) и построение ответа в одном из восьми режимов таксономии
  (`build_real_variant`). Генератор работает только с ответом, поэтому метка — смещения
  в ответе, и инвариант `answer[start:end] == span` выполняется по построению.
* Единственная нормализация текста — `normalize_text` (схлопывание пробелов); она применяется
  и при сборке, и при проверке «контекст дословно лежит в файле источника», чтобы проверка
  не расходилась со сборкой.

Режимы таксономии (баланс фиксируется при сборке, минимальное число пар на режим — 40):
`faithful`, `contradiction`, `number_attribution`, `partial`, `unconfirmed`, `missing`,
`oversight`, `excess`. Назначение каждого — «ответ сформулирован по документу, но …»:
без изменений; значение противоречит документу; значение взято у другого объекта того же
документа; приведена только часть перечня; значение не подтверждается и не опровергается;
значение отсутствует; пропущено второстепенное условие; добавлено лишнее уточнение.

Команда сборки A3 (то же, что в CI; пересборка корпуса меняет хеши и потому не выполняется
после публикации чисел):

```bash
cd spanverify-module
python3 scripts/build_corpus_a.py --real --docs data/corpus_a3/sources \
        --out data/corpus_a3 --target 1200 --seed 42   # корпус + манифест с проверками
python3 scripts/make_corpus_a3_report.py                # отчёт reports/CORPUS_A3.md
```

Пересборка меняет хеши `pairs.jsonl` и сплитов, а с ними — все опубликованные числа,
поэтому после прогона v1 корпус A3 не пересобирается (это же зафиксировано в разделе 7).

**Как получен текст A3 — читать вместе с объёмом работ.** Официальные PDF публикаций —
сканы без текстового слоя: `reports/CORPUS_A3.md`, раздел 1, фиксирует, что текст A3 получен
распознаванием (`pdftoppm` + `tesseract -l rus`), а не извлекаясь из слоя.
Это было сделано до решения заказчика `--text-only` (в отборе **новой** выборки v2 OCR
не участвует, загрузки остановлены статусом `paused`). Расхождение между способом получения
A3 и выбранным способом получения v2 — предмет решения заказчика, лист «в» в
`docs/DECISIONS_NEEDED.md`; в отчётах A3 подаётся как корпус с распознанным текстом
и соответствующей погрешностью (оценка CER распознавания для A3 не измерялась).

### Структурные проверки корпуса

Манифест `data/corpus_a3/manifest.json` заполняется на сборке и содержит **только**
результаты проверок, а не оценки человека. Актуальные значения (сверяются тестом
`tests/test_v2_docs.py` с этим же манифестом):

```json markup-checks
{
  "dataset_version": "corpus-a3.0",
  "pairs": 1200,
  "real_documents": true,
  "documents_count": 409,
  "documents_synthetic": false,
  "spans_checked": 660,
  "spans_problems": 0,
  "contexts_checked": 1200,
  "contexts_problems": 0,
  "number_attribution_checked": 132,
  "number_attribution_problems": 0,
  "plan_problems": 0,
  "clean_share": 0.45,
  "min_per_mode": 40,
  "shared_groups": 0,
  "split_train": 842,
  "split_dev": 181,
  "split_test": 177,
  "seed": 42
}
```

Что означают эти строки:

* `spans_checked` / `spans_problems` — каждый размеченный фрагмент проверен на совпадение
  границ с текстом ответа и на отсутствие пересечений; проблем нет;
* `contexts_checked` / `contexts_problems` — контекст каждой пары дословно найден в файлах
  источников; проблем нет;
* `number_attribution_checked` / `number_attribution_problems` — в режиме «атрибуции числа»
  новое число обязано найтись **в другом месте того же документа**; проблем нет;
* `plan_problems` — баланс по режимам соответствует заданию;
* `shared_groups = 0` — ни одна группа источников не попала в два сплита одновременно
  (утечку между сплитами ловит `tests/test_v2_no_leakage.py`).

## 4. Ручная верификация (способ 2)

Автоматическая разметка отвечает на вопрос «что сделал генератор», но не на вопрос
«так же ли это выглядит для человека». Поэтому методика требует ручной проверки, и
**ни одна пара не подтверждается автоматически**: след человека — файл решений.

Очередь и сервер проверки — `spanverify-module/scripts/review_server.py`:

```bash
cd spanverify-module
# 1) очередь: 10 % тестовой части корпуса A (сплошь — только span-разметка A2)
python3 scripts/review_server.py --make-sample \
    --source data/corpus_a/splits/test.jsonl \
    --queue data/review_queue/corpus_a_10pct.jsonl --share 0.10 --seed 42
# 2) проверка человеком
python3 scripts/review_server.py --queue data/review_queue/corpus_a_10pct.jsonl \
    --out data/review_queue/decisions.jsonl --port 8770
```

Формат решения — одна строка JSONL на пару:
`{"id": …, "verdict": "ok" | "wrong" | "skip", "comment": …}`. Правило `skip`: если
проверяющий не уверен, пара не считается подтверждённой и не попадает в выборку
подтверждённых; «дотянуть» её до `ok` нельзя.

Состояние на 2026-10-11: очередь `data/review_queue/corpus_a_10pct.jsonl` собрана
(18 пар), **файла решений нет — ручная верификация не выполнена**. Скрипт очереди
подготовлен агентом; проверку по нему выполняет человек, назначенный заказчиком.
Решения, внесённые агентом, экспертными не считаются и в отчёты не попадают.

## 5. Протокол экспертной span-разметки (ожидает решения заказчика)

Отдельный и более строгий слой: разметка **реальных** ответов человеком-экспертом, без
опоры на генератор. Он нужен, чтобы судить о переносе метрики с синтетики на живые тексты.
Методика фиксирует процедуру заранее, чтобы её нельзя было подстроить под результат:

1. Эксперта назначает заказчик; агент готовит очередь, формат записей и инструкцию, но
   разметку не выполняет и не «подтверждает» чужие решения.
2. Эксперт размечает **независимо от генератора**: получает `context` и `answer` без полей
   `meta.kind` и без подсказок модели; метки вносятся в том же формате `labels`.
3. Спорные случаи разрешаются по приоритету: (а) фрагмент противоречит документу → метка;
   (б) фрагмент нельзя вывести из документа (в тексте нет ни опоры, ни опровержения) → метка;
   (в) фрагмент выводим, но переформулирован → метки нет; (г) сомнения по (а)–(в) → `skip`
   с комментарием, а не «как кажется».
4. Согласие измеряется до того, как кто-либо смотрит на метрики качества: две независимые
   разметки одного подмножества, совпадение по токенам и по границам (строгий IoU ≥ 0,5),
   доля расхождений с доверительным интервалом. Порог согласия, при котором разметка
   принимается, **не задан** — это решение заказчика (лист «а» в `docs/DECISIONS_NEEDED.md`).
5. Подпись эксперта обязательна: к файлу решений прикладывается запись с ФИО, квалификацией,
   датой,версию методики и списком `doc_id`, которые эксперт видел. Без этой записи в
   документах пишется «экспертная верификация не выполнена», и никакие формулировки вида
   «верифицировано экспертом» не допускаются.

Позиции, которых агент держится при этом шаге: очередь, формат, проверка структуры и
расчёт согласия — сделаны и закрыты тестами; **назначение эксперта, порог согласия,
подтверждение объёма и подписание результатов — вне полномочий агента** и ожидаются.

## 6. Чем разметка не является (границы метода)

* Метка отражает связь «ответ ↔ конкретный фрагмент документа». Она не утверждает
  истинность ответа по внешним знаниям: ответ, верный по смыслу, но не подкреплённый
  приведённым фрагментом, помечается как недостоверный — и это осознанное поведение задачи.
* Синтетические пары A1/A3 измеряют согласованность конвейера и различимость режимов;
  они **не** измеряют качество на реальных ответах реальных пользователей.
* Сканы и PDF (без текстового слоя) в объём разметки не входят: пункт 4.1 договора их
  исключает; текстовый слой — отдельный вопрос, его доля измеряется отдельно
  (`spanverify-module/reports/v2/text_layer_yield.json`); отдельного файла-сводки в репозитории нет, числа берутся из названного артефакта.
* Числа этого документа — только результаты проверок корпуса; требования к длине текста,
  памяти и времени по пункту 4.2 договора заранее не заявляются и устанавливаются
  испытаниями (`spanverify-module/reports/FUNCTIONAL_TESTS.md`).

## 7. Изменения методики

1. Любая правка определений допустима **только до** публикации чисел соответствующего прогона;
   после — только с новой версией методики и новым прогоном (иначе «достигнуто/не достигнуто»
   теряет смысл).
2. Версия методики поднимается вместе с версией пакета; в шапке документа — та же версия,
   что в `reports/METRICS.json` (проверяет `scripts/check_numbers.py`).
3. Пороги, веса, разбиения и критерии после чисел не меняются; попытки фиксируются
   тестами `tests/test_no_test_leakage.py`, `tests/test_reported_metrics.py`,
   `tests/test_v2_no_leakage.py`.
4. Пересборка корпуса A3 после публикации чисел не выполняется: хеши `pairs.jsonl` и
   сплитов зафиксированы в манифесте; целостность корпуса и сплитов сверяют
   `tests/test_dataset_validation.py` и `tests/test_split_and_version.py`.

## 8. Что в этом документе не подтверждено (не «почти сделано»)

* Ручная верификация очереди — **не выполнена** (файла решений нет), ожидает человека.
* Экспертная разметка реальной выборки — **не начата**: нет назначения эксперта, нет
  порога согласия; лист «а» в `docs/DECISIONS_NEEDED.md`.
* Число подтверждённых пар на реальных ответах — **не измерено**; любые оценки
  «качества на реальных данных» без этого слоя считать не подтверждёнными.
