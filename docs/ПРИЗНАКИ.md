## 1. Что считается признаком и зачем он нужен

Модуль отвечает на два вопроса: **какие токены ответа не опираются на документ** (span-верификация) и **какова доля участия ИИ** (для неё достаточно ранжирования токенов по риску). Оба ответа — линейная функция от одного и того же вектора признаков токена, поэтому описание признаков и есть описание продукта, а не внутренняя заметка.

Три свойства признаков зафиксированы кодом и тестами:

1. **Только вход модели.** `spanverify/hf_grid.py` получает на вход документ и ответ; gold-разметка в вычисление не попадает — модуль про разметку ничего не знает. Признак, подсмотревший метку, сделал бы измерение фиктивным.
2. **Общая физическая величина для двух ответов.** Один и тот же вектор значений используется и для классификации токена, и для весов доли участия ИИ: «протестировали одну модель, а заявили другую» исключено конструкцией.
3. **Детерминированность.** Один seed, один проход, один кеш: бандл при `seed=42` побайтово совпадает между запусками, при `seed=7` отличается (проверено `sha256sum` и `cmp`).

Ранжирование работает, абсолютный масштаб оценок у бустинга между частями смещается — это и есть задокументированная причина, по которой в продукт вошла логистическая регрессия с изотонической калибровкой (работа 7), а не бустинг.

Итог по артефакту: AUC ниже 0,5 у `17` признаков из `36`; значимых с исходным знаком — `11`, значимых с обратным — `14`, постоянных (AUC не определена) — `1`.

Как это читать. AUC ниже 0,5 — не «признак плохой», а признак с обратным направлением: линейная модель сама присвоит ему отрицательный вес, отдельного вычитания в коде не требуется (в `spanverify/hf_grid.py` и `spanverify/features.py` инверсии знака нет — признаки подаются как есть). Если доверительный интервал накрывает 0,5, направление не установлено и вывод об информативности признака не делается ни в какую сторону.

**Совпадения, объяснимые определением, а не измерением.** Колонки `entropy_last` и `entropy_m4` на валидации дают одинаковые AUC, средние по классам и число различных значений; то же самое для `density_k1_last` и `sim_max_last`. Причина — не в данных: `spanverify/features.py::resolve_layer` не знает роль «m4» и при неразобранном имени возвращает последний слой, а `density_k`*`_last` — среднее по `k` лучшим совпадениям, и при `k = 1` это максимум. То есть из 36 колонок сетки различных признаков 34. Сетка и `resolve_layer` этим циклом не меняются: состав сетки зафиксирован протоколом, и любое его изменение — решение заказчика (лист «г» в `docs/DECISIONS_NEEDED.md`). Числа обоих дублей в таблице сохранены как есть — они измерены, а не пересчитаны.

Воспроизвести: `python3 scripts/feature_sign_check.py --grid-cache reports/hf-cache-a3 --splits data/corpus_a3/splits --bootstrap 5000 --seed 42 --out-json reports/hf_protocol/feature_signs_a3dev.json --out-md reports/hf_protocol/feature_signs_a3dev.md` (сетка v3 берётся из артефактов `grid-a3-0`…`grid-a3-3` прогона «Протокол hf (критерий ТЗ)» `38076145605`; шарды тестовой выборки `grid-test-a3-*` не скачиваются, а скрипт отвергает любой файл кеша с `test` в имени; локально прогон требует кеш, в CI — job «AUC и знак по каждому признаку сетки (val)» из `.github/workflows/hf-feature-signs.yml`).

### 3.4. Диагностика val: операционная точка, сглаживание, семейства, seed'ы

**Не измерено.** Инструмент готов: `scripts/val_diagnostics.py`, прогон — workflow
`hf-val-diagnostics.yml` (тот же кеш `grid-a3-*`, что и в 3.3; тестовая часть не читается —

### 3.5. Чего нет (и это не «почти сделано»)

* **Вклад каждого из 36 признаков в F1 на val — не измерено.** Знак и AUC по признаку измерены (3.3), но «сколько добавляет признак» без прогона ablation не утверждается; готовый измеритель — 3.4 (`scripts/val_diagnostics.py`, `--ablate all`), числа — за прогоном. Команды цикла: `make hf-grid-v2` затем `make hf-curve-v2`.
* **Отдельного замера «только признаки attention» на A3 — нет.** В v1 они входили в расширенный набор; вывод о их индивидуальном вкладе без этого замера не делается.
* **Информативность на реальных (не синтетических) размеченных данных — не измерено**, потому что реальной span-разметки нет: это блокер работ 1–2 и 3, он описан в `docs/DECISIONS_NEEDED.md`.

## 4. Как признаки участвуют в решении

```text
документ + ответ → один проход модели → для каждого токена ответа: 36 значений
  риск токена      = линейная модель (логистическая регрессия, 5 фолдов, L2 = 0,01) по этим значениям
  фрагмент (span)  = связный отрезок токенов с риском не ниже порога окна,
                   обрезка: не короче span_floor, не длиннее span_cap, склейка merge_gap
  вердикт ответа   = «есть неподкреплённые фрагменты», если доля рисковых токенов не ниже
                   порога ответа (калибровка при заданном FPR, работа 7)
  доля участия ИИ  = взвешенная доля рисковых токенов (режимы soft и hard, порог verdict_rule)
```

Пороги, веса и разбиения после публикации чисел не менялись: это проверяют `tests/test_no_test_leakage.py`, `tests/test_reported_metrics.py` и гейты `make hf-verify-v2`.

Значения по умолчанию заданы кодом: для токенов, не сопоставленных с подсловами модели, энтропийные признаки получают `DEFAULT_ENTROPY`, остальные — `0,0`. То есть отсутствие сигнала трактуется как нейтральность, а не как риск.

## 6. Ограничения, которые надо помнить при чтении любых чисел

* Признаки считаются по подсловам модели, сопоставление слову — по правилам `docs/METRIC_SPEC.md`; «значение признака токена» — агрегат по его подсловам.
* Энтропия и масса внимания зависят от архитектуры модели: смена базовой модели требует перепридумывания признака и, по пункту 5.4 договора, отдельного протокола замены.
* Все числа раздела 3 получены на синтетическом корпусе A3: они описывают поведение метода на синтетике, а не ожидаемое качество на реальных документах заказчика.
