# Журнал цикла v2 (независимая выборка, цель F1 ≥ 0,70 при FPR ≤ 0,40)

Правила цикла и определения — `docs/METRIC_SPEC_v2.md` (заморожена до измерений, её
sha256 попадает в `reports/v2/manifest.json`). Здесь — аудит перед шагом 0, правило
отбора, **предварительно зарегистрированные** гипотезы и журнал прогонов. Числа в этот
файл вносятся из артефактов (`reports/v2/*.json`), а не от руки; строка «не измерено»
оставается до тех пор, пока артефакта нет.

## Цели и правило остановки (зафиксированы до любых чисел v2)

| цель | условие на независимом тесте | что происходит при недостижении |
|---|---|---|
| внутренняя (с запасом) | F1 (токены) ≥ 0,70 при FPR (токены) ≤ 0,40 | отдельная строка отчёта со статусом PASS/NOT MET |
| контрактный минимум (ТЗ, Прил. №3, п. 4.1) | F1 (токены) ≥ 0,60 при FPR (токены) ≤ 0,40 | отдельная строка отчёта; понижать её нельзя |

Обе цели проверяются тестом `tests/test_v2_criterion.py`, и он же краснеет, если
цикл остановлен на середине. Стоп-правило шага 2 (F1_val < 0,70 после 10 гипотез)
закрывает цикл со статусом «не достигнуто на val», тест не открывается.

## Шаг 1: правило порога

**Правило цикла v2 (выбор заказчика, зафиксирован до измерений):** из порогов, при
которых `FPR_val ≤ 0,40`, берётся порог с максимальным `F1_val`; при равенстве F1 —
меньший FPR.

**Что в коде сейчас:** `choose_threshold` в `scripts/hf_protocol.py` (v1) выбирает
порог по максимуму F1 при `FPR ≤ 0,40` **по out-of-fold оценкам train** (групповая CV
по документам) — то есть правило то же по форме, но данные другие (train, а не val).
Разница зафиксирована как отдельный эксперимент на val, а не как изменение после теста:

* `E0` — правило v1 (порог из train-CV, применяется к val);
* `E1` — правило v2 (порог выбирается на val).

Оба числа репортятся на val; для шага 3 замораживается `E1` (по требованию заказчика),
а `E0` приводится рядом как несмещённая по порогу оценка. Кривая F1/FPR по сетке
порогов сохраняется в `reports/v2/val_curve.json` — чтобы видеть компромисс, а не
одну точку.

## Шаг 2: десять гипотез (предзарегистрированы до запуска)

Номер — порядок исполнения; каждая гипотеза = отдельный коммит и строка журнала.
Все решения (принято/отклонено) — по `F1_val` при `FPR_val ≤ 0,40`; test в отборе не
участвует. Рычаги ограничены списком заказчика: признаки, модель, классификатор,
агрегация, дополнительные train-данные.

| # | имя | изменение (что именно добавляется) | ожидание до прогона |
|---|---|---|---|
| 0 | `threshold-rule-v2` | только правило порога (`E1` против `E0`), признаки и модель не меняются | +0,01…0,04 к F1_val за счёт выбора на val; обязано сопровождаться второй строкой с `E0` |
| 1 | `baseline-grid-v2` | 36-признаковая сетка v1, логрег, окно 0, `merge_gap` 2 — точка отсчёта на новом корпусе | базовая линия, с ней сравниваются все остальные |
| 2 | `wide-linear-v2` | перенос лучшей конфигурации v1 (36 признаков, логрег, `l2=0,1`, 800 эпох) без перенастройки | если перенос не работает на v2 — это результат, а не повод подкручивать |
| 3 | `all-layer-entropy-v2` | энтропия внимания по всем слоям и головам (агрегация mean/max по слоям) | признак устойчивее на длинных актах, FPR ниже |
| 4 | `density-multi-k-v2` | плотность эмбеддингов при k = 1, 3, 5 и на 3 слоях | должен помочь по «неподтверждённым» добавкам |
| 5 | `lexical-numeric-v2` | лексическое и числовое совпадение токена с документом + привязка числа к объекту как признак | главный рычаг на подтипе `number_attribution` |
| 6 | `sentence-context-v2` | контекст соседних токенов и предложения (масса внимания на уровне предложения) | снижает ложные срабатывания на связках |
| 7 | `bootstrap-seed-v2` | обучение с бутстрапом по документам train (`bootstrap_docs`), seed влияет на модель | F1_val может чуть упасть; цель — осмысленный `std`, а не рост |
| 8 | `head-aggregation-v2` | агрегация по головам (max по головам вместо mean) + окно сглаживания 1 | в v1 дало худший результат; проверяем, воспроизводится ли на новом корпусе |
| 9 | `bigger-model-v2` | те же признаки, извлечённые из `ai-forever/rugpt3base` (выбор только по val) | самый дорогой по предвычислению; кандидат на основную модель, если выиграет |
| 10 | `boost-smoothed-v2` | градиентный бустинг пней на 36 признаках + сглаживание окном 2 (в v1 бустинг вырождался: F1 = 0 при AUC 0,86–0,92 — проверяем, что выбор порога больше не схлопывается) | если снова вырождается — фиксируется как отклонённая с причиной |

Стоп-правило: **если после десяти гипотез `F1_val < 0,70` при `FPR_val ≤ 0,40`, цикл
останавливается с отчётом «не достигнуто на val», тест не открывается** (решение
заказчика от 2026-10-11: «закрываем цикл»). Тестовая выборка v2 остаётся
неразпечатанной для следующего цикла.

## Отступления (обязательный раздел, заполняется по мере появления)

1. **Режим загрузки изменён агентом и поставлен на паузу.** Заказчик выбрал
   `--text-only`; прогон CI `38112679499` (2026-10-11, 15 срезов, 8 файлов-кандидатов,
   4 новых документа за 13м00с) показал цену этого режима, а измерение доли годовых
   слоёв по манифесту корпуса v1 — `python3 scripts/text_layer_yield.py --sources
   data/corpus_a3/sources/sources.json --all` — даёт 4 из 272 (доля 0,0147,
   95 % ДИ [0,0057; 0,0372]). Текстовым режимом корпус в 1500 документов не
   собирается. Исполнитель перешёл на распознавание **без подтверждения заказчика** —
   это отступление от его решения, а не техническая деталь, поэтому цепочка волн
   остановлена (`.github/corpus-v2.mode` = `paused`) и режим ждёт ответа заказчика:
   `docs/CORPUS_v2.md`, разделы 3.1 и 3.4. Уже скачанные 84 текста помечены
   `ocr_pending_approval` в `reports/v2/corpus_status.json`. Прежняя формулировка
   «≈3 % актов» снята: она не воспроизводилась командой.
2. **Волны цепляются автоматически** (job «Цепочка волн»): остановить прогон из
   песочницы нельзя — у токена нет права `actions:write` (`gh run cancel` → HTTP 403,
   проверено 2026-10-11), поэтому единственная защита от пустых прогонов —
   условие «волна должна добавить документы» и предохранитель в 24 волны.
3. **Порог выбирается на val (правило `E1`)** — по требованию заказчика; риск
   оптимистичности `F1_val` компенсируется второй строкой `E0` (порог из train-CV).
4. **Тексты источников — в ветке `data/corpus-v2-raw`, а не в рабочей ветке** — иначе
   30 МБ на каждый клон и на каждый патчсет; воспроизводится командой из
   `docs/CORPUS_v2.md`, раздел 5.
5. **Экспертную верификацию разметки подписывает человек (заказчик)**; агентская
   вычитка не записывается как человеческая. Если её нет — в отчёте стоит
   «экспертная верификация не выполнена».

## Шаг 3: заморозка конфигурации (заполняется скриптом, не от руки)

Заполняется скриптом `scripts/freeze_final_config_v2.py`, а не руками: номер и имя
конфигурации, sha256 `config/hf_final_config_v2.json`, sha256 сетки и `sweep.json`,
правило порога, seed'ы, команда `make hf-final-v2`, время заморозки и git commit.
Отдельной строкой скрипт вписывает зафиксированное число порога — на неё опирается
`tests/test_v2_docs.py`, и до появления замороженной конфигурации этой строки в журнале
быть не может (иначе число появилось бы раньше, чем его выбрали на val). До появления
этого блока шаг 3 не выполняется.
