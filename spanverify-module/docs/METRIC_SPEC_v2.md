# Спецификация метрик цикла v2 (заморожена до любых измерений v2)

Документ фиксирует определения, правило отбора и правила прогона для цикла **v2**.
Он написан и закоммичен **до** первого измерения на выборке v2; после получения
чисел его разделы изменению не подлежат (изменение = новое измерение с новой
заморозкой). Spec цикла v1 — `docs/METRIC_SPEC.md`, она тоже не правится: числа v1
остаются историей и в отборе v2 не участвуют.

## 0. Область действия и то, что запрещено

**Цель цикла v2 (формулировка заказчика от 2026-10-11):** на **новой независимой**
тестовой выборке, в режиме `hf` (реальная языковая модель, CPU):

| цель | условие | статус в отчёте |
|---|---|---|
| внутренняя цель с запасом | **F1 (токены) ≥ 0,70 при FPR (токены) ≤ 0,40** | отдельной строкой |
| контрактный минимум (ТЗ, Прил. №3 к договору 0117812, п. 4.1) | **F1 (токены) ≥ 0,60 при FPR (токены) ≤ 0,40** | отдельной строкой |

Формулировка контрактного минимума получена от заказчика текстом: файл договора PDF
в рабочей папке отсутствует, поэтому здесь он зафиксирован **как дано**, а не как
«прочитано из документа v1». Источник формулировки записан в `manifest.json`.

Запрещено (нарушение обнуляет измерение):

1. запускать любую конфигурацию на тесте A3 и на любой выборке, которую видели
   циклы v1 (A1, A3, A3-local70, demo, внешний корпус B); их результаты — только
   для истории и приводятся с пометкой «v1»;
2. подбирать порог, веса, модель или правила по тесту; смотреть на тест до шага 3;
3. менять метрики, определения и правило вердикта после получения чисел;
4. удалять трудные примеры, править gold-разметку, обрезать выборки и документы
   без записи об этом в `manifest.json`;
5. вписывать числа в отчёты руками: все числа берутся из `reports/v2/manifest.json`;
6. ослаблять тесты: невыполненный критерий показывается падением с текстом NOT MET,
   а не `skip`/`xfail`;
7. железа больше обычного CPU и 16 ГБ RAM; не урезать данные ради результата.

## 1. Единицы счёта и первичная метрика

* **Пара** = `{context, answer, labels}`; `labels` — тройки `[start, end, label]` со
  смещениями в **ответе**. Формат пары совпадает с v1 и не меняется.
* **Оцениваемый токен** — токен ответа, для которого `is_scored_token(token.text)`
  истина (`spanverify.features`). Иная выборка токенов была бы другой метрикой.
* **gold(t) = 1** ⇔ токен пересекается хотя бы с одним gold-фрагментом
  (`label == 1`): `token.start < end and token.end > start`.
* **pred(t) = 1** ⇔ `score(t) ≥ порог`. Порог один на весь прогон (раздел 3).
* **TP/FP/FN/TN** — micro-подсчёт по всем оцениваемым токенам всех пар выборки.
* **Первичная метрика — F1 по токенам.**
  `precision = TP/(TP+FP)`, `recall = TP/(TP+FN)`, `F1 = 2PR/(P+R)`.
* **FPR по токенам = FP / (FP + TN)** — доля ложных срабатываний среди токенов
  поддержанного текста. Если `FP + TN = 0`, FPR = 0. Если модель ничего не
  пометила (`TP + FP = 0`), `precision = F1 = 0`.
* **AUC** приводится как справочная величина и **не** участвует в отборе и в
  статусе критерия (ранняя формулировка спецификации v1 допускала прочтение «FPR
  ≤ 0,40» как ограничение по AUC — действует формула выше; в v2 она записана
  однозначно).
* Формулы реализованы тем же кодом, что и в v1 (`spanverify.engine._token_metrics`),
  и сверяются тестом `tests/test_metric_spec.py` — определения не «переопределяются»
  для v2, чтобы сравнение циклов имело смысл.

## 2. Вторичные уровни

* **Уровень ответов.** Ответ «помечен», если вердикт продукта `not in {grounded, empty}`
  — правило вердикта копируется из кода без изменений (в v1 оно было заморожено
  именно так). Золотой ответ ⇔ в паре есть хотя бы один gold-фрагмент.
  Micro P/R/F1 и FPR = FP/(FP+TN) по ответам.
* **Уровень фрагментов.** Предсказанные спаны: соседние помеченные токены склеиваются
  с зазором `merge_gap` (раздел 3), затем comparison с gold-спанами по жадному
  сопоставлению с **IoU ≥ 0,5**; P/R/F1 по фрагментам.
* Для каждого уровня в `manifest.json` пишутся TP/FP/TN/FN и число пар/строк, чтобы
  любое число можно было пересчитать из предсказаний.

## 3. Отбор конфигурации и правило порога (только val, до теста)

* **Правило порога (шаг 1 цикла v2):** из кандидатов-порогов, при которых
  `FPR_val ≤ 0,40`, выбирается порог с **максимальным `F1_val`**; при равенстве F1 —
  меньший FPR. Кандидаты — сами значения оценок токенов (оптимум F1 всегда достигается
  на пересечении забора с оценкой какого-то токена).
* Это правило отличается от v1, где порог выбирался по out-of-fold оценкам **train**
  (групповая CV по документам) и только потом применялся к val. Различие зафиксировано
  **до** измерений и является выбором заказчика; риск (порог и оценка отобраны на одном
  сплите → оптимистичность `F1_val`) компенсируется тем, что в отчёте обязательно
  приводится вторая строка: тот же прогноз с порогом из train-CV. Обе величины
  считаются **только на val**.
* **Выбор конфигурации:** максимум `F1_val` при `FPR_val ≤ 0,40` среди не более чем
  10 гипотез шага 2. Test в отборе не участвует ни на одном шаге.
* `merge_gap` и окно сглаживания — гиперпараметры отбора: перебираются на val,
  замораживаются до шага 3.

## 4. Шаг 3: один прогон, пять seed'ов, разброс обязателен

* Конфигурация замораживается **до** запуска: файл `config/hf_final_config_v2.json`,
  его sha256 и запись в `docs/EXPERIMENTS_v2.md` коммитятся заранее; единственный
  запуск — одной командой (`make hf-final-v2`); перезапуск с другими параметрами
  запрещён.
* **Пять seed'ов (42, 43, 44, 45, 46) на обучающей части.** На тесте сообщаются
  `mean ± std` и значения по каждому seed'у; лучший seed не выбирается.
* **Требование к разбросу (следствие дефекта, найденного в v1).** В v1 пять seed'ов
  дали идентичные числа (`std = 0,0`): линейная модель обучалась полным пакетом без
  перемешивания, и seed менял только инициализацию. Zero std означает, что «среднее
  по пяти seed'ам» — это одно измерение, а не пять. Поэтому в v2:
  1. seed обязан влиять на обучение: дополнительно к инициализации используется
     **бутстрап по документам** обучающей части (`bootstrap_docs`), отбор и порог при
     этом остаются общими для всех seed'ов;
  2. перед шагом 3 выполняется проверка `std(F1) > 0` на val
     (`scripts/hf_protocol_v2.py seedcheck`), и она закрыта тестом
     `tests/test_v2_seed_variance.py`;
  3. если после корректного способа внесения случайности std всё ещё 0 — это
     фиксируется в `manifest.json` и в отчёте как ограничение, а не замалчивается.
* Никакого подбора по тесту: test читается один раз, после чего конфигурация,
  метрики, порог и правило вердикта не меняются.

## 5. Что обязан содержать `reports/v2/manifest.json`

`protocol: hf-criterion-v2`; git commit и тег `freeze-v2-protocol`; sha256 файлов
разбиения и списки doc_id; sha256 `docs/METRIC_SPEC_v2.md` и
`docs/METRIC_SPEC.md` (преемственность определений); model id + revision; sha256
конфигурации; seed'ы и способ их влияния; hardware (выводы `lscpu`, `free -h`,
версии torch/transformers, python); время и длительность; метрики трёх уровней с
TP/FP/TN/FN и числом строк; кривые F1/FPR по порогам на val (и, если шаг 3
состоялся, на test — `reports/v2/val_curve.json`, `test_curve.json`); статусы обеих
целей (0,70 и 0,60) и `criterion_note`; список отступлений; признак сокращения
выборки (должен быть `null`); дизъюнктивность doc_id с v1 (число пересечений,
должно быть 0).

Рядом лежат `predictions_test.jsonl.gz` (по одному объекту на оцениваемый токен:
`id, level, seed, token, start, end, gold, score, pred`, `score` — 12 знаков) и
`gold_test.jsonl.gz` (`id, spans`). Числа манифеста восстанавливаются из них
независимым пересчётом (`verify-manifest`, допуск 1e-6) — это требование, а не
пожелание.

## 6. Остановка и то, как выглядит «не достигнуто»

* **Стоп-правило шага 2:** если после 10 гипотез `F1_val < 0,70` при
  `FPR_val ≤ 0,40`, цикл останавливается с отчётом «не достигнуто на val», тестовая
  выборка v2 **не открывается** (остаётся замороженной для следующего цикла).
* В этом случае `tests/test_v2_criterion.py` падает с текстом «ИЗМЕРЕНИЕ НА ТЕСТЕ НЕ
  ВЫПОЛНЯЛОСЬ: стоп-правило шага 2, F1_val = <число>» — ни `skip`, ни `xfail`.
* Если шаг 3 состоялся и цель не достигнута — статус `NOT MET` с числами и разрывом
  (`f1_gap`), без формулировок вида «почти», «практически», «в пределах погрешности».

## 7. Объём выборки (обоснование, а не минимум)

Тестовая часть должна позволять **различать** 0,70 и 0,60, а не «примерно
наблюдать». В v1 test был 177 пар / 281 gold-токен / 64 документа, отсюда
стандартная ошибка F1 ≈ 0,03–0,04, а с учётом кластеризации по документам
(design effect ×2–3) — 0,05–0,07: этим объясняется разрыв `F1_val 0,5157 → F1_test
0,5950`. Для `SE(F1) ≈ 0,015` нужно ≈1700–2000 gold-токенов, что при средней
плотности A3 (0,235 gold-токена на пару) даёт **test ≥ 600 пар**. С плотностью
пар 2,9 на документ и запасом на документы без фактов итог:

| часть | пар | документов | доля |
|---|---|---|---|
| train | ≈ 3000 | ≈ 1050 | 70 % |
| val | ≈ 640 | ≈ 220 | 15 % |
| test | ≈ 640 | ≈ 220 | 15 % |
| **всего** | **≈ 4280** | **≈ 1490** | разбиение **по документам** |

Минимум заказчика (200 пар) выполнен более чем втрое; сокращение выборки после
заморозки не допускается и проверяется тестом.
