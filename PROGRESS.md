## Шаг 1. Разведка

* Стек: Python 3.10+ без внешних зависимостей в ядре, стандартная библиотека.
  Это позволяет собирать один переносимый файл и не тянуть FastAPI/uvicorn
  внутрь `.exe`.
* Что уже было в репозитории: текстовый детектор «написан ли текст ИИ» (без
  контекста) с синтетическим корпусом и калибратором; рабочий CI, собирающий
  и публикующий `.exe`.
* Чего не было: продукта, который решает заявленную задачу «подтверждается ли
  ответ документом». Именно он и делается дальше.

**Решение.** Прежний текстовый детектор сохраняется как историческая ветка
(команда `spanverify analyze`, модули `detector.py`, `backends/`, `text.py`,
`vectors.py`, `training.py`). Он не используется продуктовыми путями
(API, интерфейс, `.exe`), но и не выбрасывается: его тесты продолжают
проходить, а сравнение двух постановок остаётся возможным. Это зафиксировано в
README.

## Шаг 2. Контракт и структура

* Принят контракт из мастер-промта: `POST /v1/verify` с полями `answer`,
  `context`, `prompt`, `max_new_tokens`, `with_tokens`; ответ содержит `score`,
  `is_hallucination`, `ai_share`, `ai_share_hard`, `threshold`, `spans`,
  `latency_ms`, `mode`, `stats`.
* Порт по умолчанию — 8765 (как в Приложении А), не 8000.
* Артефакты обучения: `config/weights.json` (+ `config/head.json`, если
  выбрана голова).

**Решение.** `ai_share` и `ai_share_hard` трактуются как доли **недостоверного**
текста (средняя калиброванная вероятность по токенам и доля токенов выше порога
маски), а не как «доля текста, написанного ИИ». Имена полей исторические и
зафиксированы контрактом, но смысл в продукте другой — это указано и в коде, и
в руководстве, чтобы числа не читались неправильно.

**Отклонение от мастер-промта (осознанное).** В промте артефакт головы назван
`config/head.npz`. Реализация — `config/head.json`: ядро продукта работает без
numpy, и добавлять бинарный формат ради имени файла значило бы тянуть
зависимость в `.exe`. Схема и смысл совпадают (тип, признаки, масштаб, веса,
смещение, метрики по фолдам); в `weights.json` поле `head.file` указывает на
`config/head.json`.

## Шаг 3. Контекстный конвейер

Сделано:

* `core.py` — токенизация с непрерывными координатами, разбиение на
  предложения и чанки, разбор чисел, результаты проверки.
* `features.py` — три признака: `attention_entropy`, `ctx_attention_mass`,
  `embedding_density`; режимы `hf` (реальная модель) и `demo` (лексические
  суррогаты без весов модели).
* `engine.py` — конвейер: признаки → риск → сглаживание → порог маски →
  склейка → расширение до границ предложения → метки → оценка ответа →
  калибровка → вердикт.
* `dataset.py` — генератор пар «контекст — ответ» с разметкой по символам.
* `train.py` — перебор весов по AUC, подбор порога маски по F1 при ограничении
  FPR, логистическая регрессия с 5-кратной кросс-валидацией, изотоническая
  калибровка, подбор порога решения по целевому FPR.
* `calibration.py` (существовал) — PAVA-калибровка и метрики.

### Найденные и исправленные ошибки (важно для доверия к числам)

1. **`numbers_in` возвращал пусто** из-за остаточного пробела при нарезке
   слова: число «5» не находилось, признак опоры молчал. Исправлено
   добавлением нормализованного слова токена.
2. **Нормировка min–max уничтожала абсолютный смысл признака**: любой ответ
   получал токен с максимальным риском. Заменено нормировкой по максимуму, а
   затем — полным отказом от нормировки признака опоры: 0 = опоры нет,
   1 = токен подтверждён.
3. **Перенормировка признака опоры по максимуму внутри ответа** делала
   «полностью подтверждённым» ответ, где слабо поддержаны все токены (все
   значения делились на слабый максимум). Признак опоры и косинусная плотность
   теперь не нормируются, нормируется только энтропия.
4. **Литеральная формула T = μ + z·σ** прятала искомую подмену за порогом:
   сама подмена увеличивала σ. Заменено на устойчивую оценку
   `median + z·1.4826·MAD` с границами `[floor, cap]`.
5. **Пунктуация и служебные слова попадали в маску** и создавали фрагменты у
   достоверных ответов. Теперь маска строится только по содержательным токенам
   (`is_scored_token`), а их риск обнуляется до сглаживания.
6. **Сглаживание окном 3 «размывало» одиночную подмену** (одна треть пика).
   Центр окна теперь весит 0.6, соседи — по 0.2; шум подавляется, узкий пик
   сохраняется.
7. **Метрики отчёта считались с нулевыми флагами** (в отчёт попадал не тот
   результат) — исправлено, и добавлена сквозная проверка через публичный
   `verify()`, чтобы обучение и выдача не разъезжались.
8. **Порог маски подбирался без головы, а в API применялся вместе с головой.**
   Теперь порог подбирается на том сигнале, который реально пойдёт в API:
   правило и голова сравниваются между собой, победитель определяется по F1
   при ограничении FPR на обучающей части.

### Демонстрационный корпус: что в нём и как проверен

240 пар, три типа: подтверждённые ответы (116), подмена значения (85),
выдуманное утверждение (39). Правила, закреплённые тестами: разметка всегда
внутри ответа; у подтверждённых ответов меток нет; выдуманный фрагмент
отсутствует в контексте; один seed — один корпус.

**Решение (упрощение демо-режима, о котором нужно знать).** Лексический
суррогат не умеет сопоставлять парафразы («составляет» ↔ «установлен в
размере»), поэтому служебные обороты считаются поддержанными документом
(`PARAPHRASE_WORDS`). Это упрощение демо-режима; в режиме `hf` таких
послаблений нет, там признак опоры считается по вниманию модели.

### Метрики (демо-режим, отложенная часть корпуса, 72 пары / 690 токенов)

| Метрика | Значение |
| --- | --- |
| token precision | 0.988 |
| token recall | 0.932 |
| **token F1** | **0.959** |
| FPR по токенам | 0.002 |
| AUC по токенам | 0.996 |
| F1 по ответам | 1.000 при пороге 1.0 (FPR 0.0) |
| полнота накрытия фрагментов | 1.000 |
| F1 при расширенной разметке | 1.000 |

Критерий качества мастер-промта (token F1 ≥ 0.90 при FPR ≤ 0.10) достигнут:
0.959 при 0.002. Метрики считаются сквозным путём — той же функцией
`verify()`, которую вызывает API.

**Честное предупреждение.** Корпус синтетический и построен по шаблонам:
числа доказывают, что конвейер работает и самосогласован, а не что он решает
задачу на реальных документах. Научные выводы требует режим `hf` и реальная
разметка — это ровно то, что делает пилот на шаге 7.

**Отдельно про строгий F1 по фрагментам.** Он равен 0.2, и это ожидаемо:
конвейер по регламенту расширяет найденный токен до границ предложения, а
разметка в корпусе узкая (одно число). Поэтому в отчётах рядом стоят полнота
накрытия (1.000) и F1 при расширенной тем же правилом разметке (1.000).
Основной критерий качества — токенный F1.

## Шаг 4. Контракт API, CLI, интерфейс

* `server.py` — HTTP-сервис на стандартной библиотеке: `GET /`, `/health`,
  `/v1/config`, `/v1/model`, `POST /v1/verify`. CORS разрешён, а заголовок
  `X-Frame-Options` намеренно не выставляется, чтобы интерфейс открывался во
  фрейме предпросмотра.
* `api.py` — оставлен как совместимый псевдоним (`from spanverify.api import
  Service`), потому что старый API жил там.
* `cli.py` — команды `verify`, `train`, `calibrate`, `evaluate`, `selftest`,
  `server`/`serve`, `demo`, `config` и историческая `analyze`; коды возврата
  0/1/2. Исторический глобальный флаг `--backend` работает и до, и после имени
  команды (это проверено тестом).
* `webui.py` — интерфейс под задачу «документ + ответ»: примеры подмены,
  выдумки и подтверждённого ответа, подсветка фрагментов, таблица токенов.
* `scripts/exe_launcher.py` — точка входа `.exe`: `--port`, `--no-browser`,
  автооткрытие браузера, выбор свободного порта, если 8765 занят.

Проверено вживую: сервис запущен на 0.0.0.0:8765, `GET /health` отдаёт режим,
порог и веса; `POST /v1/verify` с подменой числа возвращает
`verdict=likely_hallucination`, `score=1.0`, фрагмент с риском 0.775.

## Шаг 10. Доработка после первых прогонов CI (честный разбор)

Первый тег `v1.0.1` дал красный результат в двух местах: смоук-тест `.exe` и
пилот на реальной модели. Разбирательство велось по фактам, а не по догадкам.

**Найдено и исправлено (пилот).** Причина отказа пилота — не модель, а
несовместимость с веткой `transformers` 5.x, установленной в CI:

1. `tokenizer(..., return_offsets_mapping=True)["offset_mapping"]` на свежих
   версиях возвращает обычный список, а не объект с методом `.tolist()`; код
   падал с `AttributeError` ещё до расчёта признаков. Теперь смещения
   приводятся к списку кортежей и поддерживаются оба формата — и «батчевый»
   (`[[(s, e), ...]]`), и плоский (`[(s, e), ...]`).
2. Скрытые состояния не запрашивались, поэтому третий признак (плотность
   представлений) в режиме `hf` всегда был нулевым. Теперь флаги
   `output_attentions`/`output_hidden_states` ставятся в конфиге модели — это
   работает одинаково в старых и новых версиях.

Проверка велась локально на специально собранной крошечной локальной модели
(свой BPE-токенизатор + `GPT2Config` на 4 слоя): полный путь признаков
проходит для слоёв `first`/`middle`/`-4`/`last`, плотность ненулевая, пилот
пишет отчёт и считает AUC (на случайных весах ≈ 0.5 — ровно то, что должно быть).

**Честный отказ вместо выдуманных чисел.** Если признаки модели недоступны,
пилот пишет черновик отчёта с трассировкой и возвращает код 2; если контраст
групп не выдержан — отмечает это в отчёте (`status: contrast_not_met`) и
продолжает, а не подгоняет числа. Появился флаг `--fail-on-contrast` для
режима «пусть падает».

**Смоук-тест `.exe` стал диагностируемым.** Теперь вывод запущенного
приложения пишется в файлы и распечатывается в логе (в том числе при падении),
плюс печатается содержимое `release/`. Добавлена отдельная проверка
автономности: `.exe` копируется в пустой временный каталог (без папки
`config/`) и должен подняться и найти подмену — только так подтверждается
заявление «одна ссылка, ноль установок».

**Ограничение платформы.** `workflow_dispatch` через API даёт 403, пока файл
workflow не лежит в ветке по умолчанию. Поэтому прогоны запускаются тегами
(`git push origin vX.Y.Z`) — этот путь и является боевым.

**Проверка контракта порта.** Порт приложения — 8765 (как в Приложении А
мастер-промта). Если порт занят, приложение не падает, а сообщает фактический
порт и поднимается на следующем свободном.

**Найдено и исправлено (обучение и подача расходились).** В `config/weights.json`
не сохранялся выбранный при обучении предел порога фрагментов (`span_cap`):
при подаче подставлялось значение по умолчанию 0.6 вместо обученного 0.5.
Теперь `span_cap` записывается в файл параметров, а `/health` отдаёт
`weights_source` (`disk` | `embedded` | `defaults`) — и смоук-тест проверяет
именно `embedded`, то есть что `.exe` действительно несёт веса внутри себя.

**Найдено и исправлено (точка входа).** `python scripts/exe_launcher.py`
падал с `ModuleNotFoundError`, потому что Python кладёт в `sys.path` папку
скрипта, а не корень проекта. Точка входа теперь сама добавляет корень (в
собранном `.exe` эта ветка ничего не меняет). Туда же добавлен `--port-file`:
если порт 8765 занят, приложение уходит на следующий свободный, а файл с
фактическим портом читает автотест — раньше смоук-тест в этом случае просто
ждал таймаут.

## Шаг 11. Публикация и проверка релиза (подробно)

Публикация выполняется только тегом: `git push origin vX.Y.Z` → workflow
`build-and-release-exe.yml` собирает `.exe` на `windows-latest`, запускает его,
проверяет контракт, проверяет автономность (копия `.exe` в пустом каталоге без
папки `config/`) и лишь после этого публикует релиз. Всего до зелёного состояния
понадобилось четыре итерации — каждая вскрывала настоящую проблему, ни одна не
была «перезапуском в надежде»:

| Итерация | Что показал CI | Причина | Исправление |
| --- | --- | --- | --- |
| v1.1.1 | `Failed to load Python DLL … Invalid access to memory location` | стрип PE-файлов при сборке onefile | `strip` отключён на Windows; добавлена сверка SHA-256 Python DLL внутри бандла (совпадает с исходной) |
| v1.1.2 | `UnicodeEncodeError: 'charmap'` при печати русского текста | консоль раннера в cp1252 | `configure_stdio()` в точке входа + `PYTHONUTF8=1` в окружении смоук-шага |
| v1.1.3 | автономный запуск показал `weights_source = disk` | параметры искались в текущем каталоге раньше, чем в бандле | порядок поиска: рядом с `.exe` → бандл → текущий каталог; закреплено тестами |
| v1.1.4 | всё зелёное; релиз опубликован | — | — |

Дополнительно найден и исправлен разрыв обучения и работы: выбранный при
обучении верхний предел порога фрагментов (`span_cap`) не сохранялся в файл
параметров, поэтому при подаче подставлялось значение по умолчанию. Теперь
`span_cap` пишется в `weights.json`, а `/health` отдаёт `weights_source`.

## Шаг 12. Пилот: от «числа есть» к «числа что-то значат»

Первый вариант пилота считал AUC по всем токенам ответа, и это размывало эффект:
в контрастной паре отличается ровно одно число, поэтому агрегат почти не
меняется. Добавлен **парный анализ по токену значения**: для каждой пары
считается разница «без опоры минус с опорой» внутри пары (это убирает
вариативность жанра), к средним разницам строится доверительный интервал
бутстрэпом по парам. Отчёт печатает и агрегат (для прозрачности), и парный
результат.

Результат на реальной модели `rugpt3small` (48 ответов, 1384 токена, бутстрэп
5000): **признаки не разделяют группы** — AUC 0.492–0.506 по всем признакам и
слоям, парные разницы статистически неотличимы от нуля, гипотеза о
превосходстве массы внимания над энтропией не подтвердилась. Это записано в
отчёте как отрицательный результат: подгонять пороги или отбирать пары «по
результату» запрещено условиями работы, а придумывать положительный результат —
тем более.

Что из этого следует практически: демонстрационный режим и его метрики
(token F1 0.959) показывают работоспособность конвейера, интерфейса и процедуры
обучения; научная состоятельность признаков внимания небольшой модели на
подмене одного числа **не подтверждена**. Дальнейшие шаги, если тема
продолжается: более крупная модель, более сильные искажения (выдуманные
утверждения, длинные расхождения), обучение и калибровка на реальных размеченных
парах.

## Шаг 10 (аудит, команда «исправляй»): P0/P1/P2 — что было, что стало, чем доказано

Актуальные числа всех документов — в едином файле `spanverify-module/reports/METRICS.json`
(собирается `scripts/collect_metrics.py`, сверяется `scripts/check_numbers.py` в CI).
Ниже — исторические числа этапа исправлений; они намеренно не совпадают с текущими,
потому что сплит, признаки и артефакты изменились.

### P0-1. `ai_share` и «доля участия ИИ» — разные величины

* **Было**: в корневом `Заявка_поля_и_формулировки.md:30-38` обещана «интегральная
  оценка доли участия ИИ», а модуль отдавал `ai_share` — среднюю калиброванную
  вероятность недостоверности содержательных токенов. В `docs/ЗАЯВКА_поля.md`
  слова «ИИ» нет вообще: заявка и код говорили о разных вещах.
* **Стало**: добавлена отдельная величина `ai_participation`
  (`spanverify/participation.py`, пять признаков: `attention_entropy`,
  `ctx_attention_mass`, `embedding_density`, `cliche_rate`, `len_norm`),
  логистическая регрессия, средняя вероятность по содержательным токенам.
  `ai_share` оставлен как «доля недостоверного/спорного текста» и не переименован.
  Величина доступна через `GET /v1/model` вместе с `participation.calibrated_on`.
* **Чем доказано**: три кейса — канцелярит, подтверждённый контекстом:
  `ai_share=0.067`, `ai_share_hard=0.000`, `ai_participation=1.000`, вердикт
  grounded, фрагментов 0; человеческий текст: `0.000/0.000/0.057`; канцелярит без
  подтверждения: `1.000/1.000/1.000`, `likely_hallucination`, 1 фрагмент.
  Монотонность по известной доле смеси: 0.00 → 0.018, 0.25 → 0.295, 0.50 → 0.504,
  0.75 → 0.753, 1.00 → 0.971. Тесты: `tests/test_participation.py` (7).

### P0-2. Научный результат подтверждался только на синтетике

* **Было**: перенос на данные другого происхождения не измерялся; выводы опирались
  на один генератор пар.
* **Стало**: второй генератор `spanverify/corpus_alt.py` (12 субъектов, числа
  словами, другие шаблоны) и скрипт `scripts/cross_corpus.py`; результат печатается
  в лог CI и пишется в `reports/cross_corpus.json`.
* **Чем доказано** (фактический вывод команды
  `python scripts/cross_corpus.py --out reports/cross_corpus.json`):

  ```
  Внутри корпуса A (отложенная часть): token F1=0.953
  Кросс-корпус (A → B): token F1=0.731
  Падение token F1: +0.223
  ```

  FPR на чужом корпусе — 0.144, то есть критерий «F1 ≥ 0.90 при FPR ≤ 0.10» там
  **не выполняется**. Это честное ограничение: метод настроен на лексику
  генератора A. Устранение — реальные 1200 пар «вопрос–ответ» с экспертной
  разметкой (см. AUDIT.md §12).
